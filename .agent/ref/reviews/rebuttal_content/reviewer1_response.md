# Response to Reviewer 1

We thank the reviewer for the detailed assessment and for recognizing the engineering strength and extensive validation of the work. We address each point below; manuscript locations are given as (Sec/Table X).

## R1-1 — Novelty of the methodological contributions
We agree that "SFT cold-start + RL", GRPO, and interface randomization each have clear precedents, and we have removed any wording that implies these components are individually novel. We now explicitly cite CogCoM and TACO for trajectory/CoM-style data, note that Tool-GRPO applies GRPO without a new RL operator, and cite prior domain-adaptation / meta-learning work for randomization/paraphrasing. We reposition our contribution accordingly: not a new learning algorithm, but (a) the **integration** of these ingredients into a multi-turn, multi-tool orchestration framework, and (b) the **new material of this journal version** — interface-robustness Adaptive Learning (Sec 2.4), the systematic randomized generalization study (Table 4), and the V\*/HRBench tool-planning evaluation (Tables 5-6). See revised Sec 1 and Related Work.

## R1-2 — "Generalize to New Tools" cannot disentangle abstract-function understanding from robust interface mapping
We agree with this critique and have **scoped the claim** rather than overstate it. We no longer claim the model understands "abstract tool functions." We now claim only **robustness to interface-level variation** (renamed / re-described / re-ordered tools while functionality is preserved) together with cross-stage transfer, and we say so explicitly in Sec 3.3 and the Table caption. We argue this is still a deployment-relevant property: in practice tool names, argument schemas, and descriptions change across versions and providers, and brittle interface-coupling is a real failure mode. As supporting evidence we retain the tool-selection analysis (the model adopts useful tools, ignores irrelevant ones, and down-weights redundant ones), which speaks to sensible tool selection under interface change, not to mastery of genuinely novel capabilities.

## R1-3 — Transparency of closed-source model evaluation
We have clarified the protocol (Sec 4.1 and Appendix) and added a table specifying, **for every baseline, whether it received the same tool set, the same system prompt, and the same multi-step protocol**. To be fully transparent: in the main tables the proprietary models (GPT-5-20250807, Claude-sonnet-4, Gemini-2.5-flash) were evaluated **without tools, single-turn** (temperature 0, max 2048 tokens, no ICL, one question round) — i.e. a **tool-augmented open model vs. no-tool proprietary model** comparison. We now label this explicitly and, following the prior evaluation round, additionally report a **matched-protocol** comparison in which GPT-5 (and Qwen2.5-VL-7B/72B) are run **inside our tool-server framework with the same tools and multi-step protocol** ("+Tools"): GPT-5+Tools improves markedly (VSP 55.64→71.36, Jigsaw 80.10→84.50), yet our TC+TG 7B model still leads on the structured visual-reasoning tasks (VSP 97.64, Jigsaw 94.20). We soften the "surpassing GPT-5" phrasing to this precise, scoped statement (GenReasoner surpasses GPT-5 on structured visual-reasoning tasks, including when GPT-5 is given the same tools; the proprietary models retain an edge on open-ended general tasks such as WebMMU).

## R1-5 — Reward design: theoretical justification and possible reward hacking
We thank the reviewer and want to make explicit a **design intention** that the manuscript stated unclearly. The asymmetric reward is **deliberate**: tool calls incur latency and compute cost (see R1-6a: an expert-model tool call is ~2,800× more expensive than a local operator, and generation dominates end-to-end latency), so the reward is designed to elicit tool use **only when it improves correctness** — i.e., cost-aware, need-based tool use. This is precisely the adaptive behaviour the paper studies; it is a **design goal, not reward hacking**. "Solving without a tool when the model already can" is the *intended* cost-saving behaviour, not a failure mode. We now state this in Sec 2.3 and support it with evidence:

- **Tool use scales with instance difficulty (need-based investment), from full-test-set self-checks (VSP 1,100 items with the full tool set incl. Point; Jigsaw 1,000 items).** On VSP, the easier *verification* sub-task uses **2.00 tool calls/sample** and reaches **0.97 accuracy**, whereas the harder *navigation* sub-task uses **5.28 calls/sample** at 0.37 accuracy — i.e. the model spends ~2.6× more tool calls where the task is harder. Broken down by difficulty level, average tool calls rise monotonically (L1: 2.0 calls, acc 1.00 → L6: 5.26, acc 0.28 → L8: 5.42, acc 0.29). On Jigsaw the model uses tools on ~100% of instances at **3.08 calls/sample** to reach 0.88 accuracy. In every case the model invests more tool calls precisely where the task demands it — the opposite of "avoid tools when you'll need them."
- **Adopt-vs-discard behaviour (Sec 4.4).** During RL the model *increases* A\* usage on navigation (where it helps, >1.0 call/sample) while driving A\* usage toward *zero* on verification (where A\* is a distractor), keeping near-perfect 99.20 verification accuracy — again, tools are used when they help and dropped when they don't.
- **On "solving without tools has no accuracy penalty":** on VSP/Jigsaw this cannot be measured because both are perception/planning-hard and the model calls tools on ~100% of instances, so we make this specific claim on a **general task where no-tool solutions are common** (e.g. GUIChat) rather than on structured tasks, and otherwise rely on the difficulty-scaling and adopt/discard evidence above. 〖待补 E4-补: 在GUIChat/general任务上跑同一self-check, 报"答对且未用工具"子集的占比与其正确率〗

On theory: we optimize the standard GRPO objective (its convergence properties are inherited); our composite reward is **bounded reward shaping** that biases *when* tools are used and does not change the task optimum. We add this clarification and note the absence of a formal convergence proof as a scoped, honest limitation.

## R1-6 — Multi-turn cost, sample complexity, and error propagation
**(a) Latency/cost.** We now report inference cost directly (Sec 4 / Appendix): end-to-end latency distributions, a per-stage breakdown (generation / tool-execution / orchestration), per-tool times (distinguishing local operators from expert-model calls), and an **accuracy-vs-latency curve at a matched tool budget** against baselines. Measured on **full test sets (GenReasoner-7B, single H20 GPU, TP=1)**, the breakdown shows that **the tool-execution share depends entirely on the *type* of tool used**:

| Task (tool set) | generation | tool-execution | orchestration |
|---|---|---|---|
| Jigsaw (local-only: DetectBlackArea, InsertImage) | 91.0% | **0.55%** | 0.02% |
| VSP (incl. expert-model Point/Molmo-7B) | 50.8% | **48.1%** | 0.007% |

When tools are **local operators** (Jigsaw, and VSP's A\*/Draw2DPath), tool execution is **negligible (<1%)** and generation dominates. But when the pipeline invokes an **expert-model tool** (Point = Molmo-7B) many times per sample, tool execution becomes **~48%** of wall-clock. A per-tool micro-benchmark quantifies why: a **local operator (A\*) costs ~0.09 ms/call**, whereas an **expert-model call (Point/Molmo-7B) costs ~255 ms/call — a ~2,800× difference**. This is exactly the point behind our clarification that **CPS is not a wall-clock proxy**: CPS counts a 0.09 ms local op and a 255 ms expert-model call as one equal "call", so in a mixed tool set the CPS number is dominated by cheap ops while the *time* is dominated by the few expert-model calls. It also directly reframes the cost concern: the real inference cost of tool augmentation comes from expert-model tool calls, so **cost-aware, need-based use of expensive tools — precisely what the adaptive reward encourages — is where latency is actually saved** (see R1-5). (The VSP number uses a single Point worker, so tool-execution includes queueing and is an upper bound; parallel expert-model serving lowers wall-clock but not the per-call cost. 〖精度-延迟曲线待补图〗)
**(b) Sample complexity as the tool set scales.** We add a discussion and the tool-selection results under an enlarged tool set, showing the model concentrates calls on relevant tools rather than scaling calls with tool-set size. Concretely, when we expose the model at inference to an enlarged tool set (adding held-out perceptual tools GetStartPoint/GetEndPoint/GetObstacles and manipulation tools RotateImage/DrawDashLinePath on top of AStar/Point/Draw2DPath), the call distribution stays sharply concentrated: on VSP the model calls the capability-complementing A\* frequently (avg 0.77 calls/sample, 96.6% success) and Point/Draw2DPath heavily (2.11 / 0.61 calls/sample), while irrelevant tools receive near-zero calls (RotateImage 0.00, GetObstacles 0.00) and tools redundant with an already-mastered one are down-weighted (GetStartPoint 0.01). Total calls therefore do **not** scale with tool-set size — the model routes to the few relevant tools. We cite this enlarged-toolset statistic (from the prior evaluation round) rather than re-run it, since it directly answers the sample-complexity concern.
**(c) Error propagation under failed calls.** We add a controlled tool-failure study (see R2-4 / new Table X) that injects five fault types (plausible-but-wrong, missing, malformed, timeout, contradictory) into tool responses on two tasks (VSP, Jigsaw) and measures whether the model detects/reacts, recovers, or propagates the error. The model **detects and reacts to the large majority of injected faults** (VSP 0.70–1.00, Jigsaw 0.92–1.00), issuing extra reflection turns and re-calling tools, with **near-zero propagation** except for VSP-timeout (0.24) — the hardest fault, since a timeout returns no content to react to. Accuracy under early faults degrades by at most a few points on the multi-turn task (VSP, worst −6) and more on the single-shot task (Jigsaw, up to −17), reflecting the different recovery headroom of the two task structures. This characterizes error propagation quantitatively rather than leaving it as an untested edge case.
